# Tauri in this repo

Tauri v2. `src-tauri/` builds the crate `app_lib` (`lib.rs`, `main.rs`, `dapp.rs`) and the
frontend is the Vite bundle in `dist/`. Targets: Windows and Linux desktop, plus Android.

## Commands

```
npm run dev            # Vite alone in a browser (Tauri APIs will throw — guard them)
npm run desktop        # tauri dev — the real shell
npm run desktop-build  # tauri build
npm run android        # tauri android dev
npm run android-apk    # signed APK
npm run android-aab    # bundle
```

`beforeDevCommand` / `beforeBuildCommand` in `tauri.conf.json` chain to `npm run dev` /
`npm run build`, so a frontend type error stops the Tauri build too. Dev URL is `http://localhost:1420`.

## Configuration is split per platform

`tauri.conf.json` is the base and holds almost nothing — product name, identifier, build.
Everything real lives in the platform overlays, which Tauri merges over the base:

- `tauri.windows.conf.json` — frameless window (`decorations: false`, 360×640), CSP, capabilities
- `tauri.linux.conf.json`
- `tauri.android.conf.json`

**Capabilities are declared inline** under `app.security.capabilities` in those overlay
files — there is no `src-tauri/capabilities/` directory. `src-tauri/permissions/` contains
only Tauri's `autogenerated` output; do not hand-edit it.

Two capability blocks exist and the split is load-bearing:

- **`main-capability`** — the app window. Holds the window/webview/menu core permissions
  and `http:default`.
- **`browser-capability`** — the webviews that render third-party dApp pages. Grants
  exactly one command, `dapp_request`, and **no HTTP scope at all**. A page in the browser
  tab must never reach the wallet's HTTP client.

When you add a permission, add it to the narrowest capability that needs it, and add it to
each platform overlay that ships the feature. Adding anything to `browser-capability` is a
security decision — say so in the commit body.

### CSP

Set per platform in `app.security.csp`. It already allows `wasm-unsafe-eval` (hash-wasm for
Argon2id), `https:` images, and `ipc:`/`localhost` connect sources. Widening it needs a
stated reason.

## Plugins

Frontend packages and their Rust crates must stay in step (`package.json` ↔ `Cargo.toml`):

| Plugin | Used for | Scope |
|---|---|---|
| `store` | Persisted preferences, via `utility/storage.ts` | all |
| `os` | `platform()`, behind `hook/platform.ts` | all |
| `http` | Every network read the app makes | all |
| `single-instance` | One window per machine | desktop only |
| `fs` | Recovery-phrase export | desktop only |

**Why HTTP goes through Rust:** the request is made where there is no origin and no
preflight, so nothing depends on a remote server's CORS headers. Nura's own explorer sends
`Access-Control-Allow-Origin` twice, which fails a browser CORS check exactly as hard as
omitting it. The trade is documented in `Cargo.toml` and is deliberate: `http:default`
scopes to `http://*` and `https://*`, so frontend code has an origin-free, cookie-free
client to the whole internet. Keep it out of `browser-capability`.

**Desktop-only Rust dependencies are gated**, not added globally:

```toml
[target.'cfg(any(target_os = "windows", target_os = "macos", target_os = "linux"))'.dependencies]
tauri-plugin-single-instance = "2"
tauri-plugin-fs = "2"
```

`single-instance` has no mobile implementation and would fail the Android compile. Android
exports the phrase through MediaStore in Kotlin (`ExportBridge.kt`), which no WebView can
reach — so `fs` would be dead weight and one more grant on a build that never uses it.

## The multiwebview browser

`tauri = { version = "2", features = ["tray-icon", "unstable"] }`. The `unstable` feature is
what gates the multiwebview API — without it `new Webview(...)` always fails and the app
falls back to an iframe, which explorers and most dApps refuse via `frame-ancestors`. Do
not drop it.

`src/dapp.rs` holds the in-app provider. A page's request is answered by the wallet, not by
Rust, so the command parks on a `tokio::sync::oneshot` with a `time` bound for the case
where no answer ever arrives. Desktop only — Android's browser is Kotlin's and never
reaches Tauri IPC. `tokio` is in the tree for that and nothing else.

## Calling from the frontend

- Import from `@tauri-apps/api` and the plugin packages, never from a global — the config
  sets `withGlobalTauri: false`.
- **Every Tauri call throws when the app runs outside a Tauri window** (`npm run dev` in a
  plain browser). Follow `hook/platform.ts`: `try`/`catch` with a sensible default, so a
  browser preview degrades instead of blanking.
- Never let a Tauri round-trip block first paint. Startup settles its three preference reads
  with `Promise.allSettled` in `app.tsx`; the router's loader fans out its reads with
  `Promise.all`. A rejection is logged, never fatal — the app must open with no network and
  no readable store.

## Release profile

`[profile.release]` is tuned for size: `lto`, `strip`, `panic = "abort"`,
`codegen-units = 1`. Builds are slow by design; do not "fix" this.

## Never commit

`src-tauri/gen/android/keystore.properties`, `*.jks`, `*.keystore`, and anything matching
`.env*` except `.env.example`. All are already in `.gitignore` — the last API key that was
committed had to be rotated at the provider.
